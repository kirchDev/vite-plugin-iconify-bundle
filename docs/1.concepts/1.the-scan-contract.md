# The scan contract

The plugin has no registry, no manifest and no configuration listing which icons to ship. Its definition of a **used icon** is one thing: a quoted `prefix:name` literal appearing in a scanned file. Everything else — what reaches the bundle, what fails the build, what silently renders as nothing — follows from that definition and from the exact edges of it.

## How it works

`collectIconNames` is the definition, and it is exported rather than hidden inside the plugin factory precisely because the build depends on it. It takes source text and returns the names found, grouped by collection prefix. The plugin runs it over every scanned file, resolves each name against the installed `@iconify-json/*` data, and emits the union as a single virtual module.

The seam matters more than the pipeline around it. A change to what the scan sees is a change to what ships, so that behaviour is pinned by tests against the function directly, not against the virtual module — a bug there is invisible from the plugin's own interface.

## What the scan cannot see

This is the part worth internalising, because the code states the rule but not its shadow. The scan is a text search, so a name only counts when it is written **literally** and **whole**. Every construction below produces an icon that is genuinely used at runtime and genuinely absent from the bundle:

- A name assembled at runtime — an interpolated template literal, or a concatenation. There is no literal to find, so nothing is collected.
- A name in a file whose extension is not scanned, or under a directory the scan does not descend into.
- A name whose collection prefix is not in the configured list. The prefix gates the search itself, so such a name is not merely rejected — it is never looked for.

None of these fail. They render as nothing, at runtime, in a build that reported success.

## The failure model

Two kinds of mistake, and the boundary between them is the thing to know:

**Loud.** A name the scan collects that the installed collection does not have stops the build and names the icon. This is the common case — a typo in a literal — and it is deliberately fatal rather than warned about.

**Silent.** Everything in the section above. The plugin can detect only the most likely instance of it: when a scan finds no icons at all under the configured collections, which is what a wrong `collections` list usually looks like. That case warns. A partially wrong list, or one dynamic name among many literal ones, has no signal at all.

The asymmetry is intentional, but it is the asymmetry that decides how to use the plugin: **write icon names as literals, and let the build check them.** A name the scan cannot read is a name nothing checks.

## Why it's built this way

Scanning text rather than parsing it is what makes a name inside a comment count as used. That reads like a bug and is a choice: a name written into prose sends the build looking for an icon that does not exist, and that noise was preferred over the alternative failure, where a real icon goes missing without a word.
